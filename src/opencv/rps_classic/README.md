Part 1 **3자 비교**의 세 번째 다리. `yolo/rps`(딥러닝 탐지)·`mediapipe/hand_lite`(온디바이스 랜드마크 회귀)와 **같은 문제**를, 모델 학습도 사전학습 가중치 다운로드도 없이 **순수 OpenCV 고전 영상처리**만으로 푼다.

> 실사진 6장 정확도 **2/6 (33.3%)**. 손목·손끝 기하가 무너지는 지점이 명확하고, 마스크를 반칙 수준으로 완벽하게 만들어도 **가위는 어떤 파라미터로도 맞출 수 없다.** 이것이 학습된 모델이 필요한 직접적 이유다.

## 1. 파이프라인 — 5단계

```
BGR 프레임
  │
  ├─(1) 피부색 검출      skin.py      YCrCb 변환 → cv2.inRange → open/close
  ├─(2) 윤곽 + 볼록껍질  fingers.py   findContours(최대) → convexHull
  ├─(3) 손가락 세기      fingers.py   convexityDefects → 코사인 법칙 각도 → 깊이·각도 필터
  ├─(4) 손모양 판정      gesture.py   0개=바위 / 2개=가위 / 5개=보 / 그 외=UNKNOWN
  └─(5) 승패 판정        judge.py     가위>보>바위>가위, UNKNOWN이면 '판정불가'
```

전 구간에 LLM이 없다. 입력이 정수 하나이고 출력이 4가지인 전결정 함수라 모델이 기여할 여지가 없다.

### (1) 왜 HSV가 아니라 YCrCb인가

피부색 임계값의 최대 적은 **조명 변화로 값 전체가 이동하는 것**이다. YCrCb는 밝기(Y)와 색차(Cr, Cb)를 직교 축으로 분리하도록 설계된 방송용 색공간이라, 조명이 바뀌면 주로 Y만 움직인다. 그래서 **Y를 임계에서 아예 빼버리면**(`SKIN_LOWER_YCRCB`의 첫 성분이 0, `UPPER`가 255인 이유) 밝기 변화를 설계 수준에서 무시할 수 있다.

HSV의 Hue도 비슷한 의도지만 두 가지가 불리하다.

1. Hue는 **원형**(0도와 179도가 이웃)이라 빨강 근처인 피부색이 배열 양 끝으로 갈라진다. `cv2.inRange`는 선형 구간만 자르므로 범위를 두 번 잘라 OR해야 한다.
2. 채도가 낮은 픽셀에서 Hue는 수치적으로 **불안정**하다. 조명에 날아간 손등 하이라이트가 정확히 그 영역이다.

임계값 `Cr∈[133,173], Cb∈[77,127]`은 Chai & Ngan, *"Face segmentation using skin-color map in videophone applications"* (IEEE TCSVT, 1999)의 고전적 구간을 **그대로** 썼다. 픽스처에 맞춰 흔들면 "이 6장에서만 되는 숫자"가 되기 때문이다.

### (3) 손가락 개수 — 코사인 법칙

손 실루엣에서 편 손가락 **끝점**은 볼록 껍질 위에 놓이고, 손가락 **사이의 골**은 껍질 안쪽으로 파인다. `cv2.convexityDefects`가 이 오목 구간을 `(start, end, far, depth)`로 준다.

```
a = |start − end|      (far의 맞은편 변)
b = |start − far|
c = |end   − far|
cos θ = (b² + c² − a²) / (2bc)      θ = far에서의 사잇각
```

손목·손날의 완만한 굴곡은 둔각, 펼친 손가락 사이는 예각이다. 그래서 **깊이 > 10px 그리고 각도 ≤ 90도**만 "손가락 사이"로 센다.

**손가락 개수 = 골 개수 + 1** — 단, `N=0`(주먹)과 `N=1`(검지만 폄)은 **둘 다 골이 0개**라 결함 정보만으로는 원리적으로 구분되지 않는다. 그대로 두면 주먹이 영원히 1개로 읽혀 바위가 검출 불가능해지므로, 0골 구간에서만 **solidity**(컨투어 넓이 ÷ 껍질 넓이)를 추가로 본다. 주먹은 껍질을 꽉 채우고(실측 0.896), 손가락이 하나 튀어나오면 값이 떨어진다. 임계값 0.80은 실측 분포(주먹 0.896 / 보 0.744 / 가위 0.707) 사이를 가른 값이다 — **[추정] 이 6장에서 관측된 분리 지점일 뿐이다.**

### (4)(5) UNKNOWN을 억지로 판정하지 않는다

1·3·4개는 셋 중 어느 것으로도 확신할 수 없다. "가장 가까운 것"으로 반올림하면 게임은 항상 답을 내놓지만 그 답이 맞을 근거가 없다. `mediapipe/hand_lite/hand_lite/rps.py`의 원칙을 그대로 따랐다 — **세 구현의 기권 기준이 다르면 3자 정확도 비교가 사과와 오렌지가 된다.**

승패 판정도 마찬가지로, UNKNOWN이 하나라도 있으면 무승부가 아니라 `UNDECIDABLE`이다. 무승부로 뭉개면 "인식 실패"가 "비겼다"라는 정상 결과로 둔갑해, 실패율이 점수 통계에서 사라진다.

## 4. 실패 원인 분석 — 보와 가위는 **서로 다른 이유로** 틀린다

한 문장으로 뭉뚱그리면 틀린 설명이 된다. 원인이 다르므로 처방도 다르다.

### 첫 가설은 측정으로 **반증**되었다

처음 세운 가설은 "보·가위 픽스처는 손톱에 매니큐어가 칠해져 있어, YCrCb 피부색 범위 밖으로 나간 손끝이 잘리고 그래서 골이 얕아진다"였다. `output/paper_0_vis.png`를 보면 실제로 초록 윤곽이 손톱 앞에서 멈춘다.

그래서 **절제 실험(ablation)**을 돌렸다. 피부색 대신 "배경(흰색)이 아닌 것"으로 손을 자르는 **반칙 마스크**를 만들어 손톱까지 전부 손에 포함시킨 것이다(`evaluate.py`의 `oracle_mask`).

**결과: 여전히 2/6.** 가설은 원인의 일부였을 뿐 병목이 아니었다. 추측을 그대로 문서에 적었다면 틀린 원인을 남길 뻔했다.

### (1) 보(PAPER) — 골 깊이가 자릿수 단위로 갈리고, **그 사이에 손목이 낀다**

`paper_0`의 결함 깊이 상위값: **59.5px, 48.0px, 24.3px, 9.2px, 7.3px**

손을 기울여 잡으면 손가락이 **계단처럼** 배열되어, 짧은 손가락의 골일수록 급격히 얕아진다. 문제는 **손목 오목점(24.3px, 각도 148.2도)의 깊이가 손가락 골들의 중간에 낀다**는 것이다.

- 네 개의 손가락 골을 모두 받아들이는 깊이 임계값 → **손목도 함께 받아들인다**
- 손목을 각도로 걸러내려 하면(≤90도) → 가장 얕은 손가락 골(각도 122도)도 함께 탈락한다

즉 **깊이 한 축으로도, 각도 한 축으로도 분리되지 않는다.** 이 실패는 "더 좋은 마스크·임계값"으로 완화될 여지가 남아 있지만, 강건하지 않다.

### (2) 가위(SCISSORS) — **검출은 옳고 규칙이 틀렸다**

`scissors_0`는 골 2개를 **아주 선명하게** 잡는다(깊이 96.8px / 82.5px, 각도 39.5도 / 50.5도). 마스크도 기하도 실패하지 않았다.

이 픽스처의 가위 포즈는 **엄지가 펴져 있다.** 실제로 펴진 손가락은 3개이고, 골 2개(엄지–검지, 검지–중지)는 **기하학적으로 정답**이다. 틀린 것은 `가위 = 손가락 2개`라는 매핑이다.

**그런데 convexity defect에는 어느 골이 엄지 쪽인지 알 정보가 아예 없다.** 골은 익명의 오목점일 뿐 "이건 엄지다"라는 라벨이 붙지 않는다. 그래서 이 파이프라인 안에서는 해결 경로가 없다.

> MediaPipe는 21개 랜드마크로 엄지(인덱스 4)를 **이름으로 지목**할 수 있어 이 문제가 구조적으로 발생하지 않는다. `mediapipe/hand_lite`가 엄지 거리비로 판정하는 것이 정확히 이 지점이다.

### (3) 바위(ROCK)는 왜 맞았나 — 운이 아니라 구조

주먹은 골이 0개이고 solidity 0.896으로 껍질을 거의 꽉 채운다. **"아무 특징도 없음"이 곧 특징**이라 세부 기하가 필요 없다. 전통 기법이 유일하게 강한 지점이 이런 **덩어리 수준의 구분**이다.

### (4) 손끝이 일직선이면 골 검출이 통째로 무너진다 (합성 데이터로 확인)

`cv2.convexHull`은 한 직선 위의 점들 중 **양 끝만** 껍질 정점으로 남긴다. 손끝 높이가 모두 같으면 손 위쪽 전체가 껍질 변 하나가 되고, `convexityDefects`는 그 구간에서 **가장 깊은 결함 1개만** 보고한다.

합성 손으로 측정한 결과: 손끝을 호(가운데 손가락이 가장 김) 위에 놓으면 손가락 N개 → 골 N−1개가 정확히 나오지만, **손끝을 일직선에 놓으면 손가락이 3개든 5개든 골이 1개**로 뭉개진다(`tests/test_geometry.py::test_손끝이_일직선이면_골_검출이_무너진다`). 손가락을 가지런히 모으는 것이 실사용에서 흔한 동작임을 생각하면 심각한 취약점이다.

## 5. "임계값을 잘못 고른 것 아닌가" — 224개 조합 전수 탐색

정확도 2/6만 보고하면 튜닝 실패라는 반론을 반박할 수 없다. 그래서 **마스크 4종 × 깊이 8종 × 각도 7종 = 224개 조합**을 전수 탐색했다(`evaluate.py` 3절).

| 마스크 | 최고 성적 | 그때의 설정 |
|---|---|---|
| skin (YCrCb, 기본) | 3/6 | 깊이 2px, 각도 135도 |
| skin (모폴로지 없음) | **4/6** | 깊이 15px, 각도 150도 |
| oracle (반칙 마스크) | 3/6 | 깊이 2px, 각도 135도 |
| oracle (모폴로지 없음) | 4/6 | 깊이 2px, 각도 105도 |

**어떤 조합에서도 6/6이 나오지 않는다.** 격자 전체의 최대값이 4다.

그리고 스크립트가 이미지 단위로 누적한 결과, **224개 조합을 통틀어 한 번도 맞추지 못한 이미지는 `scissors_0`, `scissors_1`** 이다(`evaluate.py`가 매 실행마다 출력). 가위의 실패는 파라미터로 완화될 여지조차 없다 — 4절 (2)에서 설명한 대로 표현 방식 자체의 한계이기 때문이다.

### 상한 설정을 기본값으로 채택하지 않은 이유 — "틀린 이유로 맞은" 답

상한 4/6 설정(깊이 15px, 각도 150도)을 감사한 결과:

```
paper_0  PAPER→PAPER  O  인정된 골 4개 [35도/22px, 25도/82px, 71도/68px, 149도/25px]  ← 둔각 골에 의존!
```

네 번째 "골"은 각도 **148.7도, far=(157,233)** — **손목**이다. 진짜 손가락 골은 3개뿐이고, 손목을 손가락 사이로 오인한 덕분에 5개로 세어져 정답이 나왔다. 게다가 `rock_0`이 살아남은 것도 손목 결함이 **152.3도**라 150도 컷을 **3.6도 차이로** 겨우 넘겼기 때문이다.

> 6장짜리 표본에 맞춰 파라미터를 고르면 이렇게 **틀린 이유로 맞는 설정**을 고르게 된다. 그래서 이 프로젝트의 기본값은 상한 설정이 아니라 물리적 근거가 있는 각도 90도를 유지한다. **점수는 낮지만 정직하다.**

이 감사는 매 실행마다 자동으로 돌아간다(`evaluate.py`의 `audit_ceiling_setting`).

**[추정] 라벨의 의미** — 정확도 열은 **이 6장 픽스처에서만** 관측된 값이다. 그리고 이 픽스처는 3D 렌더 이미지에 균일한 스튜디오 배경이라, 실제 웹캠 환경(잡다한 배경, 혼합 조명, 나무 책상, 화면에 함께 들어오는 얼굴·팔)보다 전통 기법에 **오히려 유리한** 조건이다. 실사용에서는 2/6보다 더 나빠질 것으로 본다.

**[미검증]** MediaPipe·YOLO의 6/6은 이 스크립트가 잰 값이 아니라 다른 에이전트의 보고를 **인용**한 것이다. 재현하려면 각 프로젝트의 테스트를 직접 실행해야 한다.

## 7. 이 실패에서 배우는 것 — "왜 학습된 모델이 필요한가"

| 전통 기법이 요구하는 것 | 그 결과 |
|---|---|
| 사람이 **피부색 범위를 손으로 지정** | 조명·피부톤·매니큐어가 바뀌면 무너진다 |
| 사람이 **깊이·각도 임계값을 손으로 지정** | 손 크기·거리·각도가 바뀌면 무너진다 |
| 사람이 **"손가락 N개 = 무슨 손모양"을 손으로 정의** | 엄지를 편 가위처럼 정의 밖 포즈는 원리적으로 못 잡는다 |
| **가장 큰 컨투어 = 손** 가정 | 얼굴·팔·나무 책상이 함께 들어오면 무너진다 (그래서 ROI 상자가 필요하다) |

학습된 모델이 하는 일은 정확히 이 **네 개의 손튜닝을 데이터로 대체**하는 것이다. MediaPipe는 손 랜드마크 21점을 회귀해 "이건 엄지다"라는 **의미 라벨**을 제공하고, YOLO는 가위/바위/보 클래스를 직접 예측해 중간 기하를 아예 건너뛴다.

**하지만 전통 기법이 진 것만은 아니다:**

- **0바이트.** 다운로드·버전 호환·라이선스 문제가 없다.
- **모든 판정 근거가 숫자로 열려 있다.** 위 4절의 실패 분석은 이 파이프라인이라서 가능했다 — 어떤 골이 몇 도라서 탈락했는지 한 줄씩 볼 수 있다. YOLO가 틀렸을 때 같은 수준으로 원인을 캘 수 있는가?
- **바위는 2/2로 맞췄다.** 덩어리 수준의 구분에는 학습이 필요 없다.

문제와 기법을 맞추는 것이 요점이지, 최신 기법이 항상 옳은 것은 아니다.

## 9. 구현 중 만난 함정 — OpenCV 5.0 API 변경

`cv2.convexityDefects()`의 반환 형태가 바뀌었다.

| 버전 | 반환 shape | 인터넷 예제의 `defects[i, 0]` |
|---|---|---|
| OpenCV 4.x | `(N, 1, 4)` | 동작 |
| **OpenCV 5.0 (이 환경)** | **`(N, 4)`** | **`TypeError`로 죽음** |

거의 모든 튜토리얼과 LLM이 4.x 관례를 따르므로, 그대로 받아쓰면 즉시 크래시한다. `fingers.py`의 `convexity_defects()`가 `.reshape(-1, 4)`로 두 형태를 모두 흡수하고, `test_geometry.py`가 이를 회귀 테스트로 고정한다.

바이브 코딩에서 **생성된 코드를 실행해보지 않고 넘어가면 정확히 이런 것이 남는다.**

## 10. 파일 구성

```
opencv/rps_classic/
├── rps_classic/
│   ├── types.py      Gesture·Result·HandShape (cv2 의존 없음, 순수 계약)
│   ├── skin.py       (1) YCrCb 피부색 마스크 + 모폴로지
│   ├── fingers.py    (2)(3) 컨투어·볼록껍질·convexity defects·각도·손가락 개수
│   ├── gesture.py    (4) 손가락 개수 → 손모양 (순수 if문)
│   ├── judge.py      (5) 승패 판정 + AI 수 선택 (cv2 의존 없음)
│   └── pipeline.py   전체 조립 — detect(frame) → Detection
├── evaluate.py       ★ 핵심 산출물: 6장 실측 + 절제 + 민감도 + 감사 + 용량 비교
├── app.py            웹캠 데모 (미검증)
├── tests/            단위 테스트 85개
├── output/           evaluate.py 산출물 (진단 이미지 + JSON)
└── requirements.txt  opencv-python, numpy — 그게 전부다
```

`rps_classic/judge.py`와 `types.py`는 cv2를 import하지 않는다. 승패 규칙과 데이터 계약은 영상처리와 무관하므로 분리해 두면 카메라 없이도 테스트할 수 있다.
