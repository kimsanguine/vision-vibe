# 튜토리얼 — 경량 MediaPipe 손인식으로 가위바위보 판정 만들기

이 폴더의 코드는 이미 완성된 정답입니다. Part 3 도전과제(`mediapipe/webcam_tutorial/`)가
"손 랜드마크를 화면에 그리기"까지였다면, 이 튜토리얼은 그 랜드마크 좌표로
**가위바위보 손모양을 실제로 판정**하는 데까지 한 단계 더 나갑니다. 그리고
같은 판정을 YOLO로 하는 `yolo/rps`와 나란히 놓고 "학습 없이 붙이기"와
"전용 모델 구해와 학습시키기"의 차이를 체감하는 것이 목표입니다.

## 0. Part 2 · Part 3 · 이 프로젝트를 한 표로

| | Part 2(YOLO, 번호판) | Part 3(MediaPipe, 손 랜드마크만) | 이 프로젝트(MediaPipe, 가위바위보 판정) |
|---|---|---|---|
| 모델 준비 | 번호판 전용 모델을 새로 구해옴 | 구글 사전학습 모델 그대로 | 구글 사전학습 모델 그대로(동일) |
| 손모양 "판정" | 해당 없음 | 해당 없음(랜드마크만 그림) | **랜드마크 좌표를 if문으로 직접 판정**(`gesture.py`) |
| 판정에 모델을 쓰는가 | YOLO(학습 필요) | — | **안 씀** — 좌표 비교로 충분한 문제라 순수 함수로 처리 |
| 모델 크기 | 클래스 없음→전용 모델 필요 | 신경 안 씀 | **7.5MB, YOLO(114MB)와 정면 비교** |

이 프로젝트에서 가장 중요한 설계 판단 하나를 먼저 짚고 시작합니다: 손이
검출된 뒤 "이게 바위인가 보인가"를 판정하는 일은 **좌표 두 개를 비교하면
끝나는 문제**입니다. 그래서 여기엔 학습된 분류기를 쓰지 않고 `if`문을
씁니다 — "결정적으로 풀리는 문제엔 모델을 쓰지 않는다"는 원칙이 코드
구조 자체에 그대로 드러납니다.

## 1. 사전 준비 (5분)

```bash
cd mediapipe/hand_lite
python3 -m venv venv
venv/bin/pip install -r requirements.txt
```

**여기서 첫 번째로 확인할 것**: `models/hand_landmarker.task`가 이미 있는지
봅니다.

```bash
ls -la models/
```

7.5MB짜리 `.task` 파일이 보인다면 **더 받을 게 없습니다.** Part 2에서 번호판
전용 YOLO 모델을 별도로 받아와야 했던 것과 대조적으로, 이 모델은 저장소에
그대로 커밋되어 있습니다(`.gitignore`에 `models/hand_landmarker.task`가
예외 처리되어 있는 이유가 이것입니다). 같은 워크샵의 `yolo/rps`는 114MB
가중치를 `fetch_assets.py`로 실행 전에 반드시 내려받아야 합니다 — 이 차이
자체가 "구글이 이미 학습해둔 범용 태스크를 그대로 쓰는가, 내 문제 전용으로
새로 구해와야 하는가"의 실물 증거입니다.

## 2. 아키텍처부터 읽기 (10분) — 코드보다 계약을 먼저

이 프로젝트는 4개 파일이 역할을 나눕니다. **`hand_lite/types.py`부터
읽으세요** — 이게 나머지 세 파일이 주고받는 유일한 "약속"입니다.

```bash
cat hand_lite/types.py
```

핵심만 보면:

```python
@dataclass(frozen=True)
class Landmark:
    x: float   # 정규화 좌표(0~1), 픽셀이 아니다
    y: float
    z: float = 0.0

@dataclass(frozen=True)
class HandResult:
    landmarks: list[Landmark]   # 항상 21개
    handedness: str              # 'Left' 또는 'Right'
    score: float

class Gesture(Enum):
    ROCK = "바위"; PAPER = "보"; SCISSORS = "가위"; UNKNOWN = "판정불가"
```

이 타입만 알면 `landmarker.py`(MediaPipe를 아는 유일한 곳)와 `gesture.py`
(판정)와 `hud.py`(그리기)는 서로의 내부를 몰라도 됩니다. 다음 순서로
훑어보세요:

1. `hand_lite/types.py` — 계약
2. `hand_lite/gesture.py` — 판정(가장 짧고, MediaPipe/OpenCV/카메라 아무것도 import 안 함)
3. `hand_lite/landmarker.py` — 엔진(MediaPipe 실제 호출)
4. `hand_lite/hud.py` — 렌더(OpenCV+PIL)
5. `app.py` — 위 셋을 엮는 진입점

**직접 확인해보기** — `gesture.py`가 정말 아무것도 import하지 않는지:

```bash
head -20 hand_lite/gesture.py
```

`from .types import Gesture, HandResult` 한 줄뿐입니다. mediapipe도 cv2도
없습니다. 그래서 이 판정 로직은 카메라나 모델 없이 **가짜 좌표만으로 100%
테스트**할 수 있습니다 — 실제로 `tests/test_gesture.py` 17개가 그렇게
동작합니다:

```bash
venv/bin/python -m pytest tests/test_gesture.py -v
```

17개 전부 통과, 0.06초 안에 끝나는 것을 확인하세요. 카메라도 모델 파일도
필요 없었습니다.

## 3. 판정 로직 뜯어보기 (15분) — 왜 이 규칙인가

`hand_lite/gesture.py`의 `fingers_up()`을 엽니다. 검지~소지 규칙은 단순합니다:

> 손끝(TIP) y좌표가 두 번째 관절(PIP) y좌표보다 작으면 = 화면 위쪽으로
> 뻗어 있다 = 펴진 것.

```python
def _is_extended(finger):
    _mcp, pip, _dip, tip = finger
    return lm[tip].y < lm[pip].y
```

엄지는 다릅니다 — 세로가 아니라 가로로 펴집니다. **이 프로젝트는 엄지 규칙을
한 번 갈아엎었고, 그 과정이 이 튜토리얼에서 가장 중요한 대목입니다.**

처음 구현은 이랬습니다. x좌표를 비교하고, `handedness`(왼손/오른손)에 따라
부등호를 뒤집는 방식입니다:

```python
# ❌ 첫 번째 시도 — 합성 테스트는 전부 통과했지만 실사진에서 0/6이었다
if hand.handedness == "Right":
    thumb = lm[_THUMB_TIP].x > lm[_THUMB_IP].x
else:
    thumb = lm[_THUMB_TIP].x < lm[_THUMB_IP].x
```

지금 코드는 다릅니다. **"엄지가 검지 밑동에서 얼마나 벌어졌나"**를 손 크기로
정규화한 비율로 봅니다:

```python
# ✅ 현재 — 좌우도, 미러링도 묻지 않는다
ratio = distance(THUMB_TIP, INDEX_MCP) / distance(WRIST, MIDDLE_MCP)
thumb = ratio > 0.57
```

그리고 `classify()`는 다섯 개 불리언 조합으로 판정합니다: 전부 굽음=바위,
전부 펴짐=보, 검지+중지가 펴지고 약지+소지가 굽으면=가위(엄지는 묻지 않습니다),
그 외는 억지로 끼워맞추지 않고 `UNKNOWN`.

**여기서 배우는 것**: 판정 규칙에는 반드시 전제가 있습니다. 첫 번째 규칙의
전제는 "카메라 입력이 미러링되지 않았다"였고, 웹캠 모드는 거울 효과를 위해
`cv2.flip`을 쓰기 때문에 그 전제를 스스로 깨고 있었습니다. 두 번째 규칙은
**그 전제 자체가 필요 없습니다** — 거리는 좌우를 뒤집어도 변하지 않으니까요.
전제가 깨질까 걱정하며 보정하는 것보다, 전제가 없는 설계로 바꾸는 쪽이
대체로 낫습니다. 이 실패가 어떻게 발견됐는지는 5절에서 다룹니다.

## 4. 정지 이미지로 파이프라인 전체 검증 (10분) — 카메라 없이 먼저

**바로 웹캠을 켜지 않습니다.** 카메라 없이도 로드→추론→판정→렌더 전체
경로가 예외 없이 도는지 먼저 확인하는 것이 `app.py`가 `--image` 모드를
따로 만들어둔 이유입니다.

```bash
venv/bin/python app.py --image <아무_사진_경로.jpg>
```

손이 없는 사진이어도 괜찮습니다 — 목적은 "손 인식 정확도"가 아니라
"코드가 안 죽고 끝까지 도는가"입니다. 콘솔에 `[검출] 손 N개`가 찍히고
`output/` 아래에 결과 이미지가 저장되면 성공입니다. 손이 있는 사진이라면
`output/<파일명>_result.png`를 열어 랜드마크 뼈대와 한글 라벨("바위"/"보"/
"가위"/"판정불가")이 제대로 그려졌는지 확인하세요.

## 5. 웹캠 모드 — 그리고 아직 검증되지 않은 것 (10분)

```bash
venv/bin/python app.py    # Q로 종료
```

**여기서부터는 정직하게 갈립니다.** 이 프로젝트를 만든 환경에는 카메라
하드웨어가 없어, 실제 웹캠으로 손을 검출하는 성능은 **미검증**입니다.
`--image` 모드로 파이프라인이 안 죽고 도는 것까지만 확인된 상태입니다.
직접 실행해서 확인해야 할 것:

- 손을 카메라에 비췄을 때 랜드마크가 잘 잡히는지
- 바위/보/가위 세 모양이 실제로 의도한 대로 판정되는지
- 바위/보/가위가 실제로 의도한 대로 판정되는지

### 이 프로젝트가 실제로 겪은 실패 — 합성 42개 통과, 실사진 2/6

3절에서 예고한 엄지 규칙 교체가 어떻게 시작됐는지가 이 절의 핵심입니다.

당시 상태는 이랬습니다. **합성 좌표로 만든 테스트 42개가 전부 초록불**이었고,
왼손·오른손 엄지 반전까지 검증하는 테스트도 있었습니다. 그런데 옆 프로젝트
(`yolo/rps/tests/fixtures/`)에 있던 **실제 가위바위보 사진 6장**을 넣어보니
정확도가 **2/6**이었습니다.

```
paper_0.png   정답 PAPER  → UNKNOWN   손가락 01111  ← 엄지만 틀림
rock_0.png    정답 ROCK   → UNKNOWN   손가락 10000  ← 엄지만 틀림
scissors_0.png 정답 SCISSORS → SCISSORS 손가락 01100
                                        └┬┘
                          검지~소지는 6장 전부 정확. 실패는 엄지 하나.
```

원인은 둘이 겹쳤습니다. ① 픽스처가 전부 **손등이 보이는** 사진이라 x부호
규칙이 무너졌고, ② **주먹을 쥐면 엄지가 접힌 손가락 위에 얹혀** x좌표가
"펴짐"으로 읽혔습니다.

덤으로 하나 더 드러났습니다. 원래 `classify()`는 가위를 "검지+중지**만**
펴짐"으로 정의했는데, **실제 가위 사진은 엄지가 벌어져 있습니다.** 사람이
가위를 낼 때 엄지를 붙이지 않기 때문입니다. 정의가 현실과 어긋나 있었던 겁니다.

**여기서 배우는 것 (이 튜토리얼에서 가장 중요한 한 가지)**:

> 합성 테스트는 **가정이 자기 안에서 일관된가**를 증명할 뿐,
> **그 가정이 현실과 맞는가**는 증명하지 못합니다.

42개가 초록불이어도 가정 자체가 틀렸으면 전부 무의미합니다. 그래서 지금
`tests/test_gesture.py`에는 실사진 6장을 통과시키는 회귀 테스트
(`TestRealPhotoRegression`)가 들어 있습니다. **여러분이 만든 판정 로직에도
합성이 아닌 진짜 입력을 한 번은 넣어보세요.**

실습 과제: `--image` 모드로 `../../yolo/rps/tests/fixtures/`의 6장을 직접
돌려보고, 왜 검지~소지는 맞는데 엄지만 틀렸는지 좌표를 찍어보세요.

## 6. YOLO 방식과 정면으로 비교하기 (15분) — 반례부터 보기

`yolo/rps/README.md`를 열어 "모델 출처" 절을 같이 봅니다. 이 프로젝트의
`bench.py`를 실행하면(재현 방법은 아래 7절) 다음이 나옵니다:

| 모델 | 용량 |
|---|---|
| MediaPipe `hand_landmarker.task` | 7.82 MB |
| YOLO `rps_yolo11x_leeyunjai.pt`(채택 모델) | 114.42 MB |
| YOLO `rps_yolo11n_gholamreza.pt`(탈락 모델) | 5.47 MB |

"MediaPipe가 YOLO보다 가볍다"는 얼핏 당연해 보이지만, **비교 대상을 바꾸면
결론이 뒤집힙니다.** 채택된 11x와 비교하면 MediaPipe가 14.63배 작지만,
더 작은 11n과 비교하면 오히려 MediaPipe가 약 1.43배 더 큽니다. 여기서 멈추지
말고 한 걸음 더 물어보세요: **그 11n 모델은 실제로 쓸 수 있는 모델인가?**
`yolo/rps/README.md`의 "모델 출처" 표를 보면 답이 있습니다 — 11n은 3
epoch만 학습된 토이 체크포인트라 정지 이미지·영상 프레임에서 **전부 0건
검출**되어 `yolo/rps` 스스로 채택을 거부했습니다. 즉 "MediaPipe보다 작은
YOLO 모델"은 크기만 작을 뿐 실전에서 동작하지 않는 모델입니다.

**이 절에서 가져갈 습관**: 어떤 벤치마크 수치를 보든 "무엇과 비교했는가"와
"그 비교 대상이 실제로 유효한가(동작하는가)"를 함께 확인하는 것 — 크기가
작다는 사실 하나만으로는 아무것도 증명되지 않습니다.

## 7. 벤치마크 직접 재현해보기 (10분)

```bash
venv/bin/python bench.py
```

출력을 위에서부터 읽으면 두 구간으로 나뉩니다:

- **`[사실]` 모델 파일 용량** — `os.path.getsize`로 직접 잰 값이라 반박 불가.
  6절 표가 이 구간에서 나옵니다.
- **`[추정]` 추론 속도** — 이 기기, 이 순간의 CPU 부하, 합성 프레임 기준의
  관측치입니다. 다른 기기나 실제 손 사진으로는 일반화되지 않습니다.

실행 시 콘솔 중간에 **1분 load average**가 찍히는 줄을 확인하세요. 이 값이
비정상적으로 높다면(코어 수 대비 몇 배씩 높다면) 다른 무거운 프로세스가
같이 돌고 있었다는 뜻이고, 스크립트가 그 상황을 스스로 진단해 "복제 간
산포가 신뢰구간 폭보다 크면 그 신뢰구간을 인용하지 말라"고 경고합니다.
**중앙값보다 최솟값(경합이 가장 적었던 순간)을 기기 성능의 대표값으로
읽으세요** — `bench.py`가 직접 그렇게 판정합니다.

`bench.py`를 `.worktrees/` 아래 어딘가(이 문서가 있는 위치 등)에서 실행하면
YOLO 모델·실제 손 사진 비교 구간이 "파일 없음"으로 나올 수 있습니다.
`bench.py`가 스크립트 자기 위치 기준으로 `yolo/rps/`를 찾는데, worktree
구조에서는 그 상대경로가 한 단계 어긋나기 때문입니다. 6절 표처럼 온전한
비교를 재현하려면 `mediapipe/hand_lite/`(원본 위치)에서 실행하세요.

## 8. 정리 — 워크샵 발표 포인트

- Part 2(YOLO)는 "전용 모델을 못 찾으면 코드가 아예 안 짜진다"였고, Part 3
  도전과제(MediaPipe)는 "모델은 이미 있는데 라이브러리 API가 통째로 바뀌었다"
  였습니다. 이 프로젝트는 한 걸음 더 나가 "모델이 주는 좌표를 가지고 내
  로직(if문)으로 무엇을 판정할지는 사람이 설계해야 한다"는 것을 보여줍니다
  — 감지(Detection)와 판정(Recognition/Decision)은 다른 층이고, 후자에는
  꼭 모델이 필요하지 않습니다.

  MediaPipe vs YOLO11x는 14.63배, MediaPipe vs YOLO11n은 1.43배 역전 —
  같은 "MediaPipe" 모델을 놓고도 비교 대상에 따라 결론이 완전히 바뀝니다.
  학생들에게 질문으로 던지기: *"이 벤치마크 표를 나중에 발표 자료에 그대로
  가져다 쓴다면, 어떤 비교 대상을 골라야 정직한 결론이 될까?"*
